# 项目上下文（Project Context）

> 本文件回答：**这个项目为什么这样设计？** 新加入的 Agent 必须先读懂本文件，再碰任何代码或文档。

## 1. 项目是什么

一套企业绩效核算系统。每月末，系统需要完成：

1. 收集各岗位的**目标达成数据**（业务员通过飞书与 bot 对话上报 / 平台导入表）
2. 数据在妙搭应用内**交互式维护管理**（妙搭 PostgreSQL）
3. 妙搭服务端 **TypeScript 计算引擎**按既定框架完成绩效核算
4. 输出最终绩效结果（得分 → 提成/奖金），结果可存 Base / 导出结果书

## 2. 系统最终形态（2026-08-14 确认，2026-08-19 架构修订 D-022/D-023）

- **数据入口**：业务员在飞书与 bot 对话，传输每月应收集录入的达成数据（agent 报数入口是最后一步接入系统，P5）
- **数据维护**：数据在妙搭应用内**交互式维护管理**（系统运行主存储 = 妙搭托管 PostgreSQL），不在 Base 上维护
- **核算引擎**：妙搭服务端 **TypeScript 计算引擎**（唯一计算权威，规则读 Metric.Scoring_Rule_Payload 配置，不硬编码）
- **Base 的角色**：只存维护/计算的结果或导入的数据，不在上面维护；今后新建 Base 禁用关联表功能（D-024）
- **Kanban 的角色**：只用于**本系统的开发过程管理**，不参与系统上线后的日常运营

## 3. 为什么这样设计（设计哲学）

本系统要长期运行，每月都要算钱——**算错钱比算得慢严重得多**。因此：

- 宁可自动化慢一步，也要数据结构和业务规则先正确
- 宁可多一道人工复核，也不能让 Agent 静默改数
- Excel 是人看的输入层，妙搭应用是计算和展示层，Canonical Data Model（docs/data_model.md）是模型定义的唯一事实来源
- 任何计算结果必须能回答「为什么得到这个分数」——可解释、可追溯、可复核

详见 `.hermes/PROJECT_RULES.md` §1 Core System Philosophy。

## 4. 系统架构（2026-08-19 按 D-022/D-023 修订）

```
数据源（Excel 导入 / bot 报数 / 平台导入表）→ 数据校验
→ 妙搭 PostgreSQL（Canonical Data Model 的物理实现；
  schema 定义的唯一事实来源仍是 docs/data_model.md）
→ 妙搭服务端 TypeScript 计算引擎 → 绩效结果（应用内视图 + 结果书 Excel）
→ 结果/导入数据可存 Base（只进不出，不在 Base 维护）
→ 备份 = 本地定期导出（db-data-export/CSV）+ 平台 PITR 7 天
```

## 5. 校对核实的权威源（以本地文件为准，2026-08-14 确认；2026-08-19 PO 澄清定义）

**权威源 = 开发过程中校对、核实系统产出对不对的外部独立标准答案。** 系统自己写、自己存的数据（妙搭 SQL）不具备校对资格——拿自己写的东西给自己校对，永远是对的，等于没有校对（PO 2026-08-19 原话）。任何系统产出（引擎结果、导入数据）必须拿下列外部基线校对：

| 内容 | 文件 | 位置 |
|---|---|---|
| 分渠道分月预算 | 羊喜市中期预算模型_20260716_V60.xlsx（「总表-渠道二维汇总」工作表） | `1.中期预算调整项目/4.final_results/` |
| 绩效框架与核算公式 | 岗位绩效说明书汇总_20260809_V04_最新绩效框架.xlsx | `1.中期预算调整项目/3.outputs/3.岗位绩效/` |

注意：飞书 Base 上也有这两份数据的副本，但**飞书副本与本地文件如有差异，一律以本地文件为准**。
