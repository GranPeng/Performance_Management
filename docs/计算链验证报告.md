## 2. 提成与豁免的配置化验证

### 2.1 配置读取规则

1. 运营/高级主管的普通梯度提成比例：`Commission_Tier.Base_Rate × Coefficient`。
2. D-010-R1 豁免行：命中 `Exemption_Scope` 后，提成比例直接取该岗位 Active `Commission_Tier.Base_Rate`，跳过梯度与考核系数。
3. `Base_Rate` 缺失，或同一岗位的 Active 运营梯度存在多个不同基数时，验证器显式失败；不会回退到字面量默认值。
4. `--base-rate` 是只读验证覆盖参数：仅改变本地“预期值”，不写入 Base、不改公式、不改业务结果。

### 2.2 覆盖值证明

## 4. D-013 / D-014 专项覆盖（T21）

- 扩展后验证器读取 `Perf_Salary_Snapshot`、`Note`、`Employee.Responsible_Channel_IDs`、`Actual.Channel_ID` 和 `Actual.Actual_Value`。T21 模拟行的 JSON `Note` 仅用于识别专项测试场景与保留追溯参数；D-014 的预期提成基数不从 Note 取值。
- D-013 独立复算：`绩效工资快照 × 得分档位百分比 + 渠道GSV × 0.001 ÷ 对应渠道中控人数`。档位边界统一为左闭右开：`[0,60)→80%`、`[60,80)→90%`、`[80,100)→100%`、`[100,150)→110%`；150 分及以上按 D-009 取最高档 110%。验证器在每次报告写入 0/60/80/100/150 的边界结论。60 分案例（绩效工资快照 5,000、渠道 GSV 100,000、中控人数 1）为 `5,000×90% + 100,000×0.001 = 4,600`。
- 结果说明书 V03 的“输出明细（文本+计算对照）”为每条结果增加：`绩效工资基数`、`档位百分比`、`绩效工资部分金额`、`中控人数`、`渠道GSV`、`GSV提成部分金额`、`复合收入（两部分合计）`。生成器仅从 Base 读取；对 D-013 行按同期间和同负责渠道去重计算人数，并在生成后验证字段存在、D-013 行无空缺、输入/输出均为 192 行。
- D-014 独立复算：运营/高级主管的 `Commission_Base` 必须等于该员工 `Responsible_Channel_IDs` 实际关联的渠道，在同一期间全部 Active `Actual.Channel_ID` 的 GSV 求和；不应用人数或比例分摊。未维护渠道关联时标记为“跳过＋记录”，不将制作部、客服等无渠道职责的正常情形误报为差异。已覆盖一个高级主管实际关联抖音、视频号两个渠道（120,000 + 80,000 = 200,000）的样本。
