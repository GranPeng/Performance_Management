## 3. P0：必须先修复

### P0-1：绩效结果列表与详情错误假设“汇总行 + 指标明细行”两层数据

**真实数据模型**：`performance_result` 的一行是 `期间 × 员工 × 指标`。每位员工的 `monthly_total` 冗余写入其当期每一个指标行；`final_score` / `weighted_score` 是单指标值。

**已核验数据**：
- 2026-07：161 指标行，32 个员工-期间组合，每组 4–6 个指标；
- 全表：192 指标行，36 个员工-期间组合；
- 所有 192 行的 `monthly_total` 均非空。

**现有错误**：
- `server/modules/performance/performance.service.ts:64-115`：列表逐条返回指标行，未按“员工 + 期间”聚合；
- `performance.service.ts:167-190`：详情以 `monthly_total IS NULL` 找指标行，当前必然返回空；
- `performance.service.ts:118-162`：把被点击的一条指标行的 `final_score` 当作顶层“总得分”。

**线上现象**：同一员工同一期间反复出现；详情抽屉的“指标明细”显示“暂无指标明细”，总分/加权分不是该员工月度汇总。

**最小修复方向**：
1. 结果列表读模型按 `app_employee_id + app_period` 聚合为一条；
2. “月度总分”明确取共享的 `monthly_total`，且检查同组一致性；
3. 详情以聚合键取得该员工该期间全部指标行，禁止用 `monthly_total IS NULL` 判断；
4. 新增“同员工同期间多指标、每行均有 monthly_total”回归测试。

### P0-2：Dashboard 与结果书可能将同一员工月度提成按指标行重复累加

**证据路径**：
- `server/modules/calc/engine.ts:177-209`：同一员工月度提成快照写入多个指标行；
- `server/modules/calc/result-book.ts:258-289`：员工汇总使用 `reduce(sum commissionAmount)`；
- `server/modules/dashboard/dashboard.service.ts:76-105`：员工聚合后仍对 `commission_amount` 求和。

**风险**：员工有 N 条指标行时，月度提成可能被累计 N 次，影响结果书、总览总提成和财务对账。

**修复门槛**：先固定提成归属为“员工 + 期间”还是“指标级”。若为员工月度字段，聚合必须取经一致性检查的单值（如 `MAX`），不可 `SUM` 重复快照；若为指标级，则引擎必须写互不重叠的指标提成。

### P0-3：`POST /api/actuals` 录入成功后，现有计算不会使用新 Actual

**证据路径**：
- `server/modules/write/sql-write.store.ts:139-167`：新增 `app_actual` 行没有 `base_record_id`；
- `server/modules/write/write.service.ts:205-218`：只新增 Actual，未更新 `performance_result.app_actual_id`；
- `server/modules/calc/adapter.ts:102-112`：计算匹配 Actual 依赖 `base_record_id`；
- `server/modules/calc/engine.ts:123-127`：只沿已有 result→actual 关联读数。

**风险**：“数据采集录入成功”不等于“重算使用新数据”，核心业务闭环断裂。

**修复门槛**：定义 Actual→Result 的唯一归属规则；在同一事务内更新目标结果行关联；新增端到端测试，断言新增 Actual 后 preview/run 的 `actualValue` / `achievementRate` 确实变化。

### P0-4：全期间重算接口没有显式登录与授权边界

**证据路径**：`server/modules/calc/calc.controller.ts:19-31` 的 `POST /api/calc/run` 无 `@NeedLogin()`；而手工写接口有显式登录保护。

**风险**：重算会覆盖一个期间全部结果。前端确认弹窗不能替代服务端认证、角色授权和操作人审计。

**修复门槛**：添加 `@NeedLogin()`、绩效管理员授权 guard、操作人/批次留痕；按妙搭会话合同确认 CSRF 防护。

## 6. jsonb → 文本：影响判定与迁移门禁

### 当前事实

- 当前 schema 有 **40 个** `jsonb` 字段；它们均是 Base 关联壳的遗留形态；
- 前端对 `link_record_ids` 搜索为 0：前端不直接拆 jsonb，风险主要在后端 SQL / DTO / 写入与计算适配层；
- 现有后端、计算、规则、总览、结果书、写接口等约 **75 个**消费点仍依赖 `link_record_ids`；
- `responsible_channel_ids` 是唯一多值关联（online 最大 2）；其余应为单值关联；
- 关联保存值必须是目标表 `base_record_id`（`rec...`），不是妙搭 UUID，也不是业务编号。

### 迁移标准

1. **单值关联**：`text NULL`，存单个 `base_record_id`；无关联即 SQL `NULL`；
2. **多值关联**：不可逗号拼接。短期保留为 JSON 文本数组，长期优先独立关系表；
3. 规则配置类字段保持原设计，不得以“去 jsonb 化”为名误改业务配置；
4. 采用 expand/contract：先新增文本列与兼容读层 → 回填与双读校验 → 切换读写 → 观察期后才讨论删除 jsonb 原列；禁止直接 `ALTER ... TYPE text` 覆盖原数据；
5. 迁移前必须完成本报告 P0-1 的员工-期间读模型修复，避免把数据语义错误扩大到迁移。

### jsonb 迁移上线门禁

- dev 中完成字段级转换清单、空值/多值/无效引用校验；
- 所有 JSON SQL 操作、`jsonb-link.ts`、calc adapter、写接口、规则/总览/导出已改为文本合同；
- 计算结果重新对照 Base/Excel/Python 外部基线，且“每员工期间 `Σ weighted_score = monthly_total`”通过；
- 全部测试、双端 typecheck、线上页面验收通过；
- `db-env-diff` 的精确 DDL 经人工审阅；
- 生成并验证带校验和的离机 online 备份；
- 用户明确授权后，才允许 `db-env-migrate`。

## 7. 建议修复顺序

1. **建立正确的员工-期间结果读模型**：先修列表、详情、Dashboard 和结果书的聚合合同；
2. **打通 Actual→Result→计算闭环**：确保录入数据确实影响试算与重算；
3. **锁住重算与复核安全边界**：登录/授权/审计/并发状态机；
4. **补全回归测试与线上端到端验收**：将本次已发现的页面错误固化为测试；
5. **建设审计与可验证备份**；
6. **最后才做 jsonb→文本 expand/contract 迁移**；
7. 上述全部通过后，再恢复 P3c 的试算/重算/导出前端按钮工作。
