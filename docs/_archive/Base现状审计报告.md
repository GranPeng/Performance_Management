# Base 现状审计报告

## 1. 审计结论

飞书 Base「组织信息库」当前 20 张表已经覆盖组织、人员、薪资、项目渠道、绩效框架、提成梯度、预算目标、达成收集、绩效计算和结果打分等模块，但整体仍是一个可追溯性不足的原型系统，不能直接作为正式绩效核算库使用。

核心结论：

1. 预算目标现状与 V60 本地权威文件不一致。Base 只有 2026 年 5 月、4 个项目、3 类指标、120 条导入记录；V60 权威口径是 9 个渠道 × 12 个月 × 57 个预算项目，共 6,156 个渠道月度值。
2. 绩效框架现状与 V04 本地权威文件不一致。Base 绩效框架有 75 条记录；V04 权威口径是 9 个岗位、45 项 KPI。Base 中包含 30 条非 V04 岗位框架记录，且客服评分口径、部分岗位名称、单项封顶等存在偏差。
3. 提成梯度现状与 V04 本地权威文件不一致。Base 提成梯度有 81 条记录；V04 权威口径是 42 条提成梯度。Base 中存在 41 条非 V04 或空白职务梯度，兴趣电商运营缺少高档梯度，部分梯度把「不封顶」写成了固定上限。
4. 当前计算链路大量使用姓名、岗位名称、部门名称、项目名称进行查找，违反项目禁止用姓名或自然语言名称作为数据库关联键的规则。
5. 当前 Base 缺少稳定的身份、来源、时间、状态字段，无法满足 Identity / Source / Timestamp / Status 的数据治理要求。
6. 当前绩效得分公式以达成率直接换算为主，未完整实现 V04 中的分档评分、封顶、保底、奖惩和特殊规则，属于 P0 阻断级差异。

本次审计只读，未对 Base 做任何创建、更新或删除操作。

## 2. 审计口径与基准

### 2.1 权威基准

按决策 D-001，本次差异判定只以本地源文件和 T1/T2 产出为基准：

- 绩效框架与核算公式：`岗位绩效说明书汇总_20260809_V04_最新绩效框架.xlsx`
- T1 基准：`docs/绩效框架结构化规则.md`、`data/output/绩效框架结构化规则.json`
- 预算目标：`羊喜市中期预算模型_20260716_V60.xlsx` / 「总表-渠道二维汇总」
- T2 基准：`docs/预算目标结构化提取.md`、`docs/指标映射表.md`、`data/output/预算目标结构化提取.json`

飞书 Base 中的副本、公式、选项和历史数据如与本地文件不一致，一律记录为差异，不把 Base 现状反向认定为业务规则。

### 2.2 结构基准

按 `docs/data_model.md` 与项目规则，正式库至少应能映射到以下 Canonical 实体：

- Employee：人员主数据
- Organization：部门树
- Position：岗位
- Project：项目
- Project_Member：项目成员分摊
- Metric：指标定义
- Target：目标值
- Actual：实际值
- Performance_Result：绩效结果

所有核心实体必须具备稳定 ID；所有数据必须具备 Identity / Source / Timestamp / Status；所有结果必须能解释 Target → Actual → Achievement Rate → Weight → Score 的计算链。

### 2.3 差异级别定义

- 缺表：Canonical 必需实体或关键支撑表不存在，现有表无法承担对应职责。
- 缺字段：表存在，但缺少身份、来源、时间、状态、口径追溯或稳定关联字段。
- 口径不符：字段、记录、公式或选项与 V04/V60/T1/T2 基准不一致。
- 冗余：存在权威来源之外的重复表、重复记录、旧模型遗留结构或测算结构，可能污染正式口径。

## 4. 逐表审计

### 4.1 项目渠道检索

- 现状结构：7 个字段，主要是产品序列、项目对照渠道、归属项目及渠道、品牌、对应一级部门、对应二级部门；60 条记录。
- 与基准的差异：
  - 无 Project_ID、Channel_ID、Org_ID，仍以项目名称和渠道名称作为关联依据。
  - 渠道集合包含快手、京东私域、抖音内容、抖音达人、视频号内容、视频号达人等；V60 权威渠道为抖音、视频号、天猫淘宝、拼多多、京东POP、京东自营、达播、私域、外部分销。
  - Base 渠道中缺少 V60 的达播、外部分销；「天猫/淘宝」与 V60「天猫淘宝」写法不一致。
  - 无 Source、Create_Time、Status，无法判断该检索表是否为当前有效版本。
- 差异级别：缺字段、口径不符。
- 审计结论：可作为现有原型的人读检索层，但不能作为正式 Project / Channel / Organization 主数据表。

### 4.2 薪资表（待人力维护确认）

- 现状结构：42 个字段，105 条记录；包含薪资、合同、身份证、银行卡、住址、联系方式等人力与敏感信息。
- 与基准的差异：
  - 无 Employee_ID；只有自增序号，不能作为人员主键。
  - 与花名册、在职人员对照项目存在人员信息重复。
  - 无 Source、Status、Create_Time、Effective_Date，无法判断 105 条记录与花名册 82 条记录差异的生命周期原因。
  - 绩效核算所需的绩效薪资、综合工资等字段与敏感人力字段混在同一张表，权限边界不清。
- 差异级别：缺字段、冗余。
- 审计结论：不宜直接并入绩效计算层；应拆出最小薪酬输入字段，并把敏感人力信息隔离在独立人力数据源或受控表中。

### 4.3 职级对照表

- 现状结构：10 个字段，16 条记录；包含职级、序列、岗位职等、薪酬上下限、带宽等。
- 与基准的差异：
  - 无 Position_ID、Grade_ID、Org_ID。
  - 与组织架构表中的职级、职等、薪资范围存在重复表达。
  - 无来源、版本、生效状态和生效时间。
- 差异级别：缺字段。
- 审计结论：可作为职级维度参考，但必须纳入统一岗位/职级主数据，否则会继续产生多套职级口径。

### 4.4 花名册

- 现状结构：19 个字段，82 条记录；包含姓名、部门、职务、职级、项目、渠道、直属上级、入职日期、是否参与绩效考核等。
- 与基准的差异：
  - 无 Employee_ID，姓名仍是主要识别方式。
  - 无人员状态、来源、创建时间、更新时间，无法区分在职、离职、停用或历史记录。
  - 部门、一级部门、二级部门、职务、项目、渠道均使用自然语言选项，无法与 Canonical Organization / Position / Project 稳定关联。
  - 「是否参与绩效考核」来自查找，缺少人工确认状态和生效周期。
- 差异级别：缺字段。
- 审计结论：是当前最接近 Employee 的表，但还不能作为正式人员主数据表。

### 4.5 在职人员对照项目

- 现状结构：14 个字段，101 条记录；通过姓名关联花名册、薪资、项目渠道和组织信息。
- 与基准的差异：
  - 无 Project_Member_ID、Employee_ID、Project_ID。
  - 101 条记录对应 92 个姓名，存在一人多项目/多渠道场景，但没有分摊比例、生效日期、失效日期、主项目标识。
  - 大量字段来自查找，实际存储的业务键不足，姓名变化或重名会破坏关联。
  - 未记录谁维护、来源是什么、何时生效、当前是否有效。
- 差异级别：缺字段、口径不符。
- 审计结论：可作为 Project_Member 原型，但不能直接作为正式项目成员分摊表。

### 4.6 组织目标达成数据收集

- 现状结构：15 个字段，60 条记录；按项目渠道、部门、月份收集 GSV 达成、签收 ROI 达成、内容团队消耗等。
- 与基准的差异：
  - 目标值由四个项目预算表公式带出，而四个项目预算表本身不是 V60 权威结构。
  - 只覆盖 2026 年 5 月，未覆盖 V60 的 12 个月和 57 个预算项目。
  - 指标只覆盖 GSV、签收 ROI、内容团队消耗，未覆盖 T2 中所有候选映射和未映射 KPI。
  - 无 Target_ID、Actual_ID、Metric_ID、Project_ID、Org_ID。
  - 实际达成值是手工数值字段，无来源系统、上传人、上传时间、校验状态。
- 差异级别：缺字段、口径不符。
- 审计结论：是原型数据登记表，不是正式 Target / Actual 数据层。

### 4.7 岗位个人目标达成数据收集

- 现状结构：19 个字段，16 条记录；当前只覆盖视频剪辑师、主播、内容主管/编导等少数岗位。
- 与基准的差异：
  - 通过姓名查找部门、岗位、直属上级、负责项目，违反稳定 ID 关联规则。
  - 只覆盖 16 人、2026 年 5 月、部分个人指标，未覆盖 V04 全部岗位和 KPI。
  - 得分计算以达成比例直接换算，未完整实现 V04 的分档评分、封顶、保底和豁免规则。
  - 无 Actual_ID、Metric_ID、Employee_ID、Source、Timestamp、Status。
- 差异级别：缺字段、口径不符。
- 审计结论：只能作为个人达成登记原型，不能作为正式 Actual 或计算输入表。

### 4.8 组织绩效达成计算

- 现状结构：15 个字段，32 条记录；通过姓名、部门、岗位、项目渠道关联组织目标达成数据。
- 与基准的差异：
  - 只计算 GSV 与 ROI 相关组织指标，未覆盖 V04 全部组织指标和岗位指标。
  - 计算方式以达成率直接换算为主，未按 V04 评分标准执行分档得分。
  - 通过姓名和自然语言部门/岗位/项目查找，关联不稳定。
  - 无 Result_ID、Metric_ID、Employee_ID、Period_ID、计算版本、计算状态。
- 差异级别：缺字段、口径不符。
- 审计结论：是组织指标计算草稿，不是正式 Performance_Result。

### 4.9 当月绩效计算

- 现状结构：13 个字段，3 条记录；输出提成结算和绩效薪资计算。
- 与基准的差异：
  - 只覆盖 3 人，不能代表正式月度核算结果。
  - 绩效得分、提成梯度、绩效比例均通过姓名和岗位名称查找，链路脆弱。
  - 无 Result_ID、计算批次、计算版本、审核状态、人工复核状态、错误日志。
  - 结果未完整保留 Target、Actual、Achievement Rate、Weight、Score 的解释链。
- 差异级别：缺字段、口径不符。
- 审计结论：当前结果表只能验证原型链路，不具备正式出数条件。

  - 多个单项最高分与 V04 评分标准中的封顶口径不一致，例如部分应按 150 分、120 分或 110 分封顶的指标在 Base 中写成 100 分、90 分或 120 分。
  - 无 Metric_ID、Position_ID、Rule_Version、Source_Sheet、Source_Cell、Source_SHA256。
  - 提成梯度查找只预留 0 至 3 四档，不能覆盖 V04 中超过四档的岗位梯度。
- 差异级别：缺字段、口径不符、冗余。
- 审计结论：当前绩效框架不能作为正式指标定义表，需要按 V04 重建。

### 4.17 提成梯度

- 现状结构：13 个字段，81 条记录；包含职务、岗位、梯度等级、得分上下限、提成系数、提成比例、提成来源等。
- 与基准的差异：
  - V04 权威口径为 42 条提成梯度；Base 为 81 条。
  - Base 中存在 41 条非 V04 或空白职务梯度，包括 DTC渠道销售、达人商务、平面设计师、平台电商运营、加粉客服及空白职务记录。
  - 兴趣电商运营在 V04 中有 7 档，Base 仅覆盖至第 4 档，缺少高档梯度。
  - 兴趣电商运营高级主管最后一档在 Base 中写成固定上限 200，而 V04 原文为不封顶口径。
  - 直播中控/运营助理缺少 V04 中的人数相关提成口径和绩效工资比例口径。
  - 电商客服专员梯度未保留 V04 的奖励条件及金额口径。
  - 无 Commission_Tier_ID、Metric_ID、Position_ID、Source_Sheet、Source_Cell、Rule_Version。
- 差异级别：缺字段、口径不符、冗余。
- 审计结论：当前提成梯度不能作为正式提成规则表，需要按 V04 重建。

### 4.18 组织架构表

- 现状结构：15 个字段，145 条记录；混合维护一级部门、二级部门、部门、岗位职务、职级、职等、序列、绩效工资占比、提成参数等。
- 与基准的差异：
  - 无 Org_ID、Position_ID、Parent_Org_ID。
  - 145 条记录只能归纳为 48 个部门岗位文本，存在大量重复，缺少唯一约束和生命周期状态。
  - 部门、岗位、职级、提成参数混在一张宽表，实体边界不清。
  - 与花名册、职级对照表、绩效框架、提成梯度存在多份岗位/部门/职级口径。
- 差异级别：缺字段、冗余。
- 审计结论：当前表不是稳定的 Organization / Position 主数据，需要拆分并建立 ID 体系。

### 4.19 测算数据表

- 现状结构：7 个字段，4 条记录；用于 ROI 场景测算和提成比例试算。
- 与基准的差异：
  - 不对应 V04/V60 的权威结构。
  - 无来源、版本、状态、负责人和有效期。
  - 与提成梯度、绩效框架存在重复表达。
- 差异级别：冗余。
- 审计结论：属于临时测算表，不应进入正式核算链路。

### 4.20 绩效得分结果（负责人打分）

- 现状结构：20 个字段，175 条记录；包含姓名、人员、部门、岗位、指标类型、分项目明细、自动计算部分、负责人填写部分、单项得分、最终得分等。
- 与基准的差异：
  - 通过姓名关联人员、岗位、项目、部门和指标，违反稳定 ID 关联规则。
  - 当前只覆盖 2026 年 5 月、32 个姓名、9 类岗位。
  - 负责人填写部分只有 10 条非空，负责人打分输入覆盖不足。
  - 自动计算部分承接上游原始达成率换算，未完整实现 V04 分档评分和特殊规则。
  - 无 Result_ID、Metric_ID、Employee_ID、Period_ID、Rule_Version、Review_Status、Source_Timestamp。
  - 结果未按正式 Performance_Result 要求保留完整 Target → Actual → Achievement Rate → Weight → Score 解释链。
- 差异级别：缺字段、口径不符。
- 审计结论：是当前最接近结果明细的表，但必须重构为按指标粒度的正式结果表。

## 5. 关键差异汇总

### 5.1 缺表

1. 缺少独立的 Channel 维度表；当前渠道只是选项或文本。
2. 缺少独立的 Position 主数据表；岗位混在组织架构表、花名册、绩效框架和提成梯度中。
3. 缺少标准化的 Metric 表；绩效框架表混入岗位、部门、提成查找和旧模型记录。
4. 缺少标准化的 Target 长表；预算目标散落在导入表和四个项目预算副本中。
5. 缺少标准化的 Actual 长表；目标达成导入为空，达成收集表是原型宽表。
6. 缺少标准化的 Performance_Result 长表；结果分散在组织绩效达成计算、绩效得分结果、当月绩效计算中。
7. 缺少导入错误日志表和计算批次表，无法满足自动化失败可追踪要求。

### 5.2 缺字段

所有核心表普遍缺少以下字段类别：

- 稳定 ID：Employee_ID、Org_ID、Position_ID、Project_ID、Channel_ID、Metric_ID、Target_ID、Actual_ID、Result_ID。
- 来源追溯：Source、Source_File、Source_Sheet、Source_Cell、Source_SHA256。
- 时间与版本：Create_Time、Update_Time、Effective_Start、Effective_End、Rule_Version、Import_Batch。
- 状态控制：Status、Import_Status、Validation_Status、Review_Status、Active_Flag。
- 计算解释：Target_Value、Actual_Value、Achievement_Rate、Weight、Score、Manual_Score、Final_Score、Calculation_Batch_ID。

### 5.3 口径不符

1. Base 预算目标只覆盖单月、4 项目、3 指标；V60 是 9 渠道、12 月、57 项目。
2. Base 渠道与 V60 渠道集合不一致，存在快手、京东私域、内容/达人子渠道，缺少达播、外部分销。
3. Base 绩效框架 75 条，V04 为 45 条。
4. Base 提成梯度 81 条，V04 为 42 条。
5. 客服 KPI 的目标、公式、评分标准与 V04 原文不一致。
6. 多个单项最高分与 V04 封顶口径不一致。
7. 组织与个人得分计算以达成率直接换算，未完整执行 V04 分档评分。
8. 高级主管部分提成梯度把不封顶口径固化为固定上限。
9. T2 已标记的签收 ROI、团队产出数量、个人成片数量、个人素材数量等未映射项，在 Base 中仍以正式目标字段参与计算，口径风险高。

### 5.4 冗余

1. 四个项目预算表彼此结构重复，并与预算目标导入表重复。
2. 绩效框架中有 30 条非 V04 岗位记录。
3. 提成梯度中有 41 条非 V04 或空白职务记录。
4. 组织架构表、花名册、薪资表、职级对照表之间重复维护人员、部门、岗位、职级和薪资信息。
5. 测算数据表为临时测算结构，不应进入正式链路。

## 6. 架构判断

按 Architecture Decision Record 格式记录本次审计判断：

### 决策

将当前 Base「组织信息库」判定为原型参考库，不判定为正式绩效核算库。正式库应先按 Canonical Data Model 重建主数据、指标、目标、实际值和结果表，再迁移或重写现有公式链路。

### 原因

当前 Base 与 V04/V60 本地权威源存在 P0 级口径差异，且缺少稳定 ID、来源追溯、时间版本和状态控制。如果直接在当前结构上补公式，会把错误口径固化为系统规则，后续返工成本更高。

### 影响

- 后续 Base 建设不能只做字段级修补，需要先完成数据模型重构。
- 现有 20 张表可作为字段参考和历史原型参考，但不能直接作为正式规则来源。
- T2 标记的未映射 KPI 不得在未确认前进入正式自动计算。
- 薪资和人员敏感信息需要与绩效计算层隔离或最小化暴露。

### 风险

- 业务侧可能已在当前 Base 中维护单月数据，重构时需要安排只读归档和迁移窗口。
- 旧表名称和字段名称已被公式引用，直接删除会破坏现有视图和公式；应先建新模型，再切换，再归档旧结构。
- 本地 V04/V60 仍有待业务确认事项，正式规则冻结前需要 Product Owner、业务、财务完成确认。
