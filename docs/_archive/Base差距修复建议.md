# Base 差距修复建议

## 1. 修复原则

本文件只提出修复建议，不对飞书 Base 做任何实际修改。

修复顺序必须遵守项目优先级：数据模型正确 > 业务规则正确 > 数据流稳定 > 自动化效率 > 用户体验。

任何字段设计必须先回答三问：

1. 为什么需要？
2. 谁产生？
3. 谁消费？

任何业务公式、评分规则、提成规则的修改，必须经过 Business Analyst、Finance Controller、Product Owner 三方确认。

## 2. 优先级总览

| 优先级 | 建议 | 目标 | 影响范围 |
|---|---|---|---|
| P0-1 | 先冻结 Canonical 数据模型和 ID 体系 | 阻断自然语言关联继续扩散 | 全部 20 张表现状 |
| P0-2 | 重建 Target 预算目标长表 | 对齐 V60 的 9 渠道 × 12 月 × 57 项目 | 预算目标相关 6 张表 |
| P0-3 | 重建 Metric 绩效指标表 | 对齐 V04 的 9 岗位 × 45 KPI | 绩效框架、组织架构、计算表 |
| P0-4 | 重建 Commission_Tier 提成梯度表 | 对齐 V04 的 42 条梯度 | 提成梯度、绩效框架、当月绩效计算 |
| P0-5 | 重建 Actual 与 Performance_Result | 保证结果可解释、可追溯、可复核 | 达成收集、组织计算、个人计算、结果表 |
| P1-1 | 拆分人员、组织、岗位、项目主数据 | 建立稳定主数据边界 | 花名册、薪资、组织架构、项目渠道、在职人员对照项目 |
| P1-2 | 建立导入批次、校验、错误日志 | 满足自动化可追踪和失败可查 | 所有导入和计算链路 |
| P2-1 | 归档旧模型与临时测算结构 | 降低口径污染和误用风险 | 非 V04 记录、项目预算副本、测算数据表 |

## 3. P0 修复建议

### P0-1：先冻结 Canonical 数据模型和 ID 体系

建议先建立或确认以下实体边界，再给 Base 补字段或改公式：

1. Employee
   - 职责：人员主数据。
   - 必要字段：Employee_ID、姓名、人员状态、入职日期、离职日期、来源、创建时间、更新时间。
   - 产生方：人力或经确认的人员主数据导入流程。
   - 消费方：花名册、项目成员、达成收集、绩效结果、薪资计算。

2. Organization
   - 职责：部门树和组织层级。
   - 必要字段：Org_ID、部门名称、Parent_Org_ID、层级、生效开始、生效结束、状态。
   - 产生方：组织主数据维护流程。
   - 消费方：人员、岗位、预算归属、绩效归属、看板筛选。

3. Position
   - 职责：岗位定义，不与部门混写。
   - 必要字段：Position_ID、岗位名称、岗位状态、职级、序列、来源、版本。
   - 产生方：组织/人力主数据维护流程。
   - 消费方：人员、绩效框架、提成梯度、结果计算。

4. Project 与 Channel
   - 职责：项目和渠道的独立维度。
   - 必要字段：Project_ID、Project_Name、Channel_ID、Channel_Name、品牌、状态、来源。
   - 产生方：业务主数据维护流程。
   - 消费方：预算目标、达成收集、项目成员、绩效结果。

5. Metric
   - 职责：绩效指标定义。
   - 必要字段：Metric_ID、Position_ID、评价维度、指标名称、权重、目标描述、计算口径文本、评分标准、评分类型、数据来源、评价周期、规则版本、源工作表、源单元格。
   - 产生方：经确认的 V04 规则迁移流程。
   - 消费方：目标、实际值、绩效结果、负责人打分、看板解释。

6. Target
   - 职责：目标值事实表。
   - 必要字段：Target_ID、Metric_ID 或预算项目 ID、Period、Project_ID、Channel_ID、Org_ID、Target_Value、单位、来源文件、来源工作表、来源单元格、来源文件哈希、导入批次、导入状态。
   - 产生方：V60 导入流程。
   - 消费方：达成率计算、绩效结果、预算分析。

7. Actual
   - 职责：实际达成事实表。
   - 必要字段：Actual_ID、Metric_ID、Period、Employee_ID、Project_ID、Channel_ID、Org_ID、Actual_Value、单位、数据来源、采集时间、上传人、校验状态。
   - 产生方：业务员上报、平台数据导入、人工登记。
   - 消费方：达成率计算、绩效结果、复核看板。

8. Performance_Result
   - 职责：按人员、期间、指标粒度保存绩效结果。
   - 必要字段：Result_ID、Period、Employee_ID、Metric_ID、Target_ID、Actual_ID、达成率、权重、单项得分、负责人打分、最终得分、规则版本、计算批次、复核状态。
   - 产生方：飞书计算引擎。
   - 消费方：当月绩效计算、提成结算、复核看板、审计追踪。

建议新增或确认 ID 规则后再动表结构；不要在现有姓名/部门/岗位文本关联上继续叠加公式。

### P0-2：重建 Target 预算目标长表

建议以 V60 结构化提取结果为唯一来源，重建统一 Target 表，而不是继续维护「预算目标导入 + 四个项目预算表」。

目标结构：

- 一行代表一个期间、一个渠道、一个预算项目的目标值。
- 先覆盖 V60 的 9 个渠道、12 个月、57 个预算项目，共 6,156 个渠道月度值。
- 保留源工作表、源渠道、源单元格、原公式、缓存值、来源文件哈希。
- 渠道必须先映射到 Channel_ID，不允许用「天猫/淘宝」「快手」「京东私域」等未确认口径直接入库。
- 项目归属、部门归属通过 Project_ID、Org_ID 关联，不通过文本包含匹配。

对现有表的建议：

- 「预算目标导入」可保留为历史参考，但不要继续作为正式 Target。
- 「伊利高个子预算目标」「伊利少年状元预算目标」「伊利骨能预算目标」「美赞臣跃高预算目标」建议在正式 Target 建成后只读归档。
- T2 已标记不能直接映射的指标，不得在正式 Target 中强行补值；先进入待确认清单。

### P0-3：重建 Metric 绩效指标表

建议以 T1 的 45 项 KPI 为唯一基准重建 Metric 表。

修复要点：

1. 只保留 V04 覆盖的 9 个岗位、45 项 KPI。
2. 为每项 KPI 分配 Metric_ID。
3. 岗位通过 Position_ID 关联，不用岗位名称直接关联。
4. 「编导」与「内容主管/编导」的名称差异通过 Position_ID 和岗位别名解决，不通过复制 KPI 解决。
5. 保留 V04 源工作表、源单元格、源编号、评分标准原文、数据来源、评价周期。
6. 电商客服专员相关 KPI 必须先恢复 V04 原文口径；Base 当前奖励/处罚金额口径不得自动进入正式规则。
7. 单项封顶、保底、评分类型应按 V04 原文结构化，不能从 Base 当前「单项最高分」反推。
8. 非 V04 的 30 条岗位框架记录建议从正式 Metric 范围剔除，转入历史参考区。

### P0-4：重建 Commission_Tier 提成梯度表

建议以 V04 的 42 条提成梯度为唯一基准重建提成梯度表。

修复要点：

1. 每条梯度分配 Commission_Tier_ID。
2. 通过 Position_ID、Metric_ID 或提成来源规则 ID 关联，不用职务名称模糊匹配。
3. 保留得分下限、得分上限、系数、比例、提成来源、规则说明、源单元格。
4. 对「不封顶」使用明确的开放上限语义，不写成固定 200 或其他数值。
5. 补齐兴趣电商运营缺失的高档梯度。
6. 补齐直播中控/运营助理的人数相关口径和绩效工资比例口径；该类口径未确认前只做结构化存储，不直接写计算逻辑。
7. 电商客服专员梯度保留 V04 的奖励条件及金额原文，不改成空值。
8. 非 V04 的 41 条梯度建议转入历史参考区，待业务确认是否另建规则模型。

### P0-5：重建 Actual 与 Performance_Result

建议把「数据登记」和「绩效达成计算」拆成事实层、计算层、结果层：

1. Actual 事实层
   - 只存实际值和采集证据，不写绩效结论。
   - 支持业务员上报、平台导入、人工补录三类来源。
   - 每条实际值必须落到 Metric_ID、Period、Employee_ID 或 Org_ID 或 Project_ID 或 Channel_ID。
   - 保留上传人、上传时间、来源说明、校验状态。

2. Calculation 计算层
   - 按 Target + Actual 计算达成率和单项得分。
   - 必须实现 V04 的分档评分、封顶、保底、豁免和特殊规则。
   - 计算结果必须能回溯到 Target_ID、Actual_ID、Rule_Version、Calculation_Batch_ID。
   - 不允许 Agent 直接修改业务结果。

3. Performance_Result 结果层
   - 按人员、期间、指标粒度保存最终结果。
   - 保留负责人打分、自动得分、最终得分、复核状态。
   - 当月绩效计算只消费 Performance_Result，不重新拼接上游宽表。

对现有表的建议：

- 「组织目标达成数据收集」「岗位个人目标达成数据收集」可作为 Actual 原型参考，不建议直接升级为正式 Actual。
- 「组织绩效达成计算」「绩效得分结果（负责人打分）」「当月绩效计算」应在正式结果层建成后切换，不建议在当前公式链路上继续补丁式修复。
- 「目标达成导入」当前为空模板，建议直接按 Canonical Actual 重新设计。

## 4. P1 修复建议

### P1-1：拆分人员、组织、岗位、项目主数据

建议把现有主数据相关表拆清边界：

- 花名册：升级为 Employee 主数据表，增加 Employee_ID 和人员生命周期状态。
- 组织架构表：拆成 Organization 与 Position 两类主数据，不再把部门、岗位、职级、提成参数混在一张宽表。
- 职级对照表：作为 Position 或职级维度的一部分，增加版本和生效状态。
- 项目渠道检索：拆成 Project、Channel、Project_Channel_Map，不再用公式拼接文本做主键。
- 在职人员对照项目：升级为 Project_Member，使用 Employee_ID + Project_ID + Channel_ID + 生效周期 + 分摊比例。
- 薪资表：只向绩效层开放计算必需字段，敏感人力字段应隔离或严格权限控制。

### P1-2：建立导入批次、校验和错误日志

建议新增三类支撑结构：

1. Import_Batch
   - 字段：Batch_ID、来源类型、来源文件、来源哈希、导入时间、导入人、状态、记录数、成功数、失败数。
   - 用途：预算导入、实际达成导入、人员导入统一追踪。

2. Validation_Rule
   - 字段：Rule_ID、校验对象、校验类型、校验口径、严重级别、启用状态。
   - 用途：校验必填字段、ID 存在性、期间合法性、目标/实际值类型、渠道映射、指标映射。

3. Error_Log
   - 字段：Error_ID、Batch_ID、对象类型、对象 ID、错误类型、错误内容、处理状态、处理人、处理时间。
   - 用途：满足自动化失败必须生成错误日志、禁止静默失败的项目规则。

## 5. P2 修复建议

### P2-1：归档旧模型和临时测算结构

建议在正式模型切换后处理：

- 非 V04 的 30 条绩效框架记录。
- 非 V04 或空白职务的 41 条提成梯度记录。
- 四个项目预算副本表。
- 测算数据表。
- 旧的自然语言关联公式和查找字段。

处理方式建议为只读归档，不建议立即删除，避免误删业务侧仍在参考的数据。

### P2-2：建立口径确认清单

以下事项必须由业务、财务、Product Owner 确认后再进入正式规则：

1. V60「主营业务收入」是否等同于绩效中的退货后 GSV。
2. 签收 ROI 的预算目标来源。
3. 岗位与负责渠道、负责项目之间的正式映射关系。
4. 项目组、个人、素材 90 天归因数据来源。
5. 电商客服奖励/处罚金额是否属于正式绩效规则。
6. 高级主管新项目免责提成和达成激励的结构化表达方式。
7. 超过现有梯度上限的绩效得分如何处理。

## 6. 建议实施顺序

1. 先确认 Canonical 数据模型与 ID 规则。
2. 迁移 V60 到统一 Target 长表，并完成 6,156 个值的数量校验。
3. 迁移 V04 到统一 Metric 与 Commission_Tier 表，并完成 45 项 KPI、42 条梯度的数量校验。
4. 建立 Employee、Organization、Position、Project、Channel、Project_Member 主数据。
5. 建立 Actual 事实层和导入校验、错误日志。
6. 建立 Performance_Result，并按 V04 规则重写计算链。
7. 并行保留旧 Base 只读一段时间，确认新链路结果可人工复核后切换。
8. 切换完成后再归档旧模型、旧副本和测算表。

## 7. 不做事项

在未完成上述 P0 修复前，不建议做以下事项：

- 不建议在当前 20 张表上继续叠加新公式。
- 不建议用现有 Base 中的预算目标副本直接计算正式绩效。
- 不建议把 Base 当前绩效框架和提成梯度当成规则来源。
- 不建议让 Agent 直接修改绩效结果或提成结果。
- 不建议继续用姓名、部门名、岗位名、项目名做数据库关联键。
